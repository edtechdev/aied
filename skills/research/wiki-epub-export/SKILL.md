# Wiki EPUB & PDF Export

Generates and maintains the wiki's offline book-form deliverables — `aied.epub` and `aied.pdf` — containing the home intro, Use-with-AI page, all concepts (grouped by umbrella chapters), and FAQs.

## When to use
- User asks to regenerate/update `aied.epub` / `aied.pdf`, add/remove content, restructure chapters, or fix TOC / reader-rendering / front-page issues.
- Any site content change that should be reflected in the offline versions (concept/FAQ edits, renames, new pages).

## Build & delivery model (IMPORTANT)
- Built **locally** by **`PATH="$HOME/.local/bin:/usr/bin:$PATH" /usr/bin/python3 tooling/build-epub.py`**; outputs land in **`public/aied.epub`** and **`public/aied.pdf`** and are **COMMITTED** to the repo (same pattern as `llms-full.txt` / `llms.txt`).
- **The interpreter matters — do not use a bare `python3`.** The build's two halves run under *different* interpreters: the PDF is rendered by `pandoc`, which spawns the **`weasyprint` console script** (so it runs under *that script's shebang interpreter*), while the `/Lang` metadata step does `import pikepdf` **in-process** (so it runs under *whatever you invoked*). Invoking with a Python that lacks `pikepdf` used to produce a complete PDF that silently omitted `/Lang`, which is how an English PDF once shipped with no language metadata; `_require_pikepdf()` now exits 1 instead. `/usr/bin/python3` has both packages.
- The EPUB/PDF title, site URL, editor name + contact, repo/issues URLs, and license are all read from **`site.config.json`** at the repo root (the single source of truth — see the `research-wiki` skill). Do NOT hardcode them in `build-epub.py` or in this skill; edit the config instead, then regenerate.
- NOT generated in CI — do NOT add it to `npm run build` or install pandoc in GitHub Actions. This is a deliberate decision (build locally, commit).
- **NOT served from the Pages site.** `astro.config.mjs` has a `strip-offline-editions` plugin (`apply: 'build'`, `enforce: 'post'`) that deletes every `.epub`/`.pdf` from `dist/` in `closeBundle()`, because GitHub packs already-compressed files into the Pages artifact at full weight (~161 MB), which pushes it toward the 1 GB limit and the 10-minute deploy timeout. So `https://edtechdev.github.io/aied/aied.epub` returns **404 by design** — a 404 there is NOT a failed deploy.
- The download links point at `offlineBaseUrl` in `site.config.json` — currently `https://github.com/edtechdev/aied/raw/refs/heads/main/public`, so `.../public/aied.epub` and `.../public/aied.pdf`. Those resolve from the pushed commit, so they update only after a push, never from a local rebuild.
- The llms files DO stay in the build and are served from the site (`/aied/llms.txt`, `/aied/llms-full.txt`, `/aied/llms-concepts.txt`) because they are plain text and compress well.
- **Do NOT attach the EPUB/PDF files in chat responses** — the user fetches them from the GitHub Pages site. Confirm the update in text and give the URLs.
- The site's "Read the Knowledge Base Offline" section (`src/components/pages/AiPage.astro`, wrapped by `src/pages/ai.astro`) links both versions and notes they contain only the concept + FAQ pages (not the hundreds of article summaries).

## Rebuild steps
1. `PATH="$HOME/.local/bin:/usr/bin:$PATH" /usr/bin/python3 tooling/build-epub.py` — writes `dist/aied-export.md`, runs pandoc for the EPUB (post-processes the zip into `public/aied.epub`), runs pandoc + **weasyprint** for the PDF (`public/aied.pdf`), then normalizes the PDF's `/Lang` with **pikepdf**. Both packages must be installed for the interpreter that runs the build (`python3 -m pip install --user weasyprint pikepdf` — the sandbox's Python is managed, so a system-wide install is refused and `--user` puts the `weasyprint` script in `~/.local/bin`, which pandoc finds on PATH). The script now **exits 1** when `pikepdf` is missing from the invoking interpreter, printing the interpreter and the exact install command, so a missing engine cannot silently omit `/Lang`.
2. **Verify the PDF's `/Lang`, do not trust the exit code.** Read the catalog back with pikepdf (`pdf.Root.Lang`) — `pdfinfo` does not print it. Expect `en-US` for the default edition and the locale code for a translated one.


**The PDF step is no longer slow — but it still must not run beside a site build.** Since the chunked
parallel parse (`tooling/pdf_parallel.py`, `AIED_PARALLEL_CHUNKS`, default 8), a full English rebuild
takes ~4 minutes instead of ~25, and a translated edition the same order. The parse of the whole
export is what used to dominate (measured 757 s per parse, twice per build, growing superlinearly
with document size); WeasyPrint's pagination is only ~89 s. `AIED_PARALLEL_CHUNKS=1` restores the old
single-pass path. Verification is unchanged in kind: compare the new artifact's extracted text
(pages, per-chapter counts, word multisets) against the one it replaces, because a fast build that
silently drops content is worse than a slow correct one.

**Do not run this while a site build is in flight (2026-09-17).** The builder writes `dist/aied-export.md`, the EPUB, and then the PDF from that
markdown; `astro build` clears `dist/` before writing it. Run the two concurrently and the markdown is deleted between the EPUB and PDF steps, and the
PDF step dies with `FileNotFoundError: dist/aied-export.md` AFTER the EPUB has already been replaced. The epub then looks fine and is easy to ship
without noticing the PDF is stale. Rule: run the artifact builder on its own, or re-run it after any site build.
3. `git add public/aied.epub public/aied.pdf tooling/build-epub.py && git commit && git push`.
4. Verify the Deploy workflow goes green (Build & Verify + Deploy).
5. Confirm live files reflect changes — but against the RIGHT URLs: `curl -sIL https://github.com/edtechdev/aied/raw/refs/heads/main/public/aied.epub` must report the exact byte count the builder produced, and the llms files at `https://edtechdev.github.io/aied/llms*.txt` must report theirs. Never verify the edition by fetching `/aied/aied.epub`: that path is stripped from the artifact on purpose and 404s even on a healthy deploy.

## Content selection & structure (shared by EPUB & PDF)
- **Front matter:** page 1 = cover image (`public/epub-cover.png`, generated by `tooling/gen-epub-cover.mjs` with sharp); page 2 = **Notice** page; page 3 = **Table of Contents**.
- **Notice page:** title/`<h1>` = "Notice", includes the book title, an editor credit line, a statement that the ebook was **produced by an AI agent working for a human editor** and dedicated to the public domain under **CC0**, the **CC0 badge image** (inlined as a data-URI), the **disclaimer** "AI-generated output may contain inaccuracies or errors", a note that the document contains the concept and FAQ pages but **not** the hundreds of article summaries on the site (with a link to the site), a note that the **source code** is in the GitHub repository, a **how-to-report-issues** line matching the site footer (report on GitHub / contact the site developer), and the generation date. Since 2026-09-22 it also carries the **reader-facing AI-use disclosure**, built from `site.config.json` so it cannot drift from the per-page record: the models named in `aiDisclosure.models`, the fact that drafts are reviewed, corrected and published by the editor, that concept/FAQ pages are syntheses across the article summaries, that **no AI system is listed as an author or contributor**, what the scripts verify (citations against the publisher record, figures against the extracted sources), the models on record with the date each took over, and a pointer to `AI-USE.md` in the repository. The editor credit line and the disclosure both come from `contributors` / `aiDisclosure` — never hardcode a name or a model in `build-epub.py`, and remember that a policy change needs a rebuild for the book to carry it.
- **Chapters:** Introduction, Use This Knowledge Base with Your Own AI Assistant, then concepts grouped by the umbrella headings parsed from `src/data/conceptIndex.ts` (each concept at H3 under its group H2), then Frequently Asked Questions (with a short intro, each FAQ at H3). Then a closing **Free Tools and Resources** chapter (2026-09-20): a short intro, then `content/en/resources/*.md` grouped by the FIRST declared `resource_type` under H2 group labels (each resource at H3), each entry opening with a small fact list (Open it / Made by / Source code / Type · Access · License / Link checked) built from frontmatter, and closing with a `## Connected Resources` list when `connected_resources` is set. Resources go LAST on purpose: they point outside the knowledge base, so they read as a toolbox at the back of the book. Grouping order in `build-epub.py` (`RESOURCE_GROUP_ORDER`) mirrors `src/pages/resources.astro` — change both together.
- **Resource links rot.** Before a rebuild, run `python3 tooling/scripts/check-resource-links.py` (network-bound, so deliberately not part of `run-gates.py`) and fix or remove anything dead; it can bump `last_verified` with `--update`.
- **FAQ ordering:** ascending by `created` frontmatter (earliest first) so the Top-10 findings FAQ appears first.
- The Introduction and Use-with-AI chapters are extracted live from `src/pages/index.astro` / `src/pages/ai.astro` (HTML→markdown), so they always match the site — do NOT hardcode them.

## KDP / Kindle variant (aied-kdp.epub)
For publishing to Amazon KDP, a standard EPUB3 upload is enough (Amazon converts to KPF on their side; there is NO local KPF/pandoc target). Produce a hardened copy from the main EPUB:
- `python3 tooling/build-kdp-epub.py` reads `public/aied.epub` and writes `dist/aied-kdp.epub` (then copy to `public/` to serve/commit).
- The only real fix it makes: after cover.xhtml was rewritten from an SVG wrapper to `<img role="doc-cover">`, the OPF manifest still declares `properties="svg"` on that item — a stale property that confuses cover detection. Remove it; keep `properties="cover-image"`.
- Re-assert metadata KDP expects (dc:title, dc:language=en, dc:identifier, fresh `dcterms:modified`), confirm nav + ncx present.
- Verify: all member XML well-formed; cover-image declared; 0 broken internal anchors (9.3k+ in this book).
- **Caveat:** this is as far as local validation can go. Amazon's proprietary validator runs only in the KDP upload preview; Kindle Previewer is a GUI app with no Linux build. Watch two things in that preview: (a) the very deep TOC (~230 entries, 3 levels) — Kindle may flatten/truncate nested navigation; fix = trim nav depth for the KDP copy; (b) cross-page concept→concept anchor jumps.

## Key pitfalls (all hard-won)
1. **EPUB TOC hierarchical numbering must be HARD-CODED, not CSS counters.** Many e-readers ignore `::before { content: counter(...) }`. Inject literal numbers (`1`, `1.1`, `1.2.1`) directly into the `<a>` text of each nav entry during post-processing.
2. **PDF TOC numbering: the user prefers numbers ONLY in the TOC, not on body headers.** Use CSS counters scoped to `#TOC` (WeasyPrint renders counters reliably); do NOT prefix concept/FAQ body headings with numbers.
3. **PDF links must be blue/clickable-looking** (`a { color: #0b5aa0 }` in `tooling/pdf-style.css`), or users won't recognize them as links. The PDF uses `--toc` + weasyprint to make the TOC entries actual internal jump links.
4. **Left-align the EPUB TOC with `!important`.** Readers center TOC items by default; use `nav#toc * { text-align: left !important; }`. Non-`!important` rules lose to reader defaults.
5. **Keep subsections on one page:** pass `--split-level=3` so each concept (H3) and its H4 subsections live in ONE chapter file.
6. **Strip the leading title H1 from FAQ bodies.** Most FAQ `.md` files open with `# <title>` (often after a blank line). If left, it duplicates the H3 you add and splits the FAQ into two chapters + two TOC entries. Match loosely (blank lines tolerated) and delete the matching H1.
7. **Remove stray empty heading lines.** Some concept bodies contain a lone `#` (no text). pandoc turns these into phantom `section` headings that break TOC nesting. Filter out lines matching `^#{1,6}\s*$`.
8. **Back-to-Contents links are misleading — do not add them.** EPUB readers can't reliably provide `history.back()`, so a "Back to Contents" link only jumps to the TOC, not history-back. The user asked to remove them.
9. **Relabel the landmarks nav too, not just the page `<title>`.** The reader's outline/progress list labels the second page from the `landmarks` nav (`epub:type="titlepage">…`), not the document `<title>`. When renaming a front page, update BOTH the document `<title>`/`<h1>` AND the landmarks nav label, or the outline still shows the old label.
10. **Rename the TOC title** to "Table of Contents" (pandoc defaults it to the book title).
11. **No named HTML entities in EPUB XHTML.** Only the five XML-predefined entities (`&amp; &lt; &gt; &quot; &apos;`) are valid. Named entities like `&mdash;` (used on the Notice page) cause strict readers (e.g. Thorium on Windows) to fail parsing. Use a literal character or a numeric entity instead.
12. **Caret citations (`^[[slug]]`) are deprecated.** The maintainer prefers minimizing footnote-style citations when authoring. In-source they are now parenthesized hyperlinks `([[slug]])`. The EPUB/PDF link converter strips a leading `^` (so `^[[slug]]` renders as a normal link, not a footnote) — but the source convention is `([[slug]])`.
13. **A chapter title listed twice in the TOC means the H1 dedup is comparing markup, not text.** The export prefixes each chapter with its own heading and drops a page H1 that duplicates it; the site pages put an inline `<svg>` icon inside the H1 ahead of the words, so a verbatim comparison never matches and the title ships twice. Compare the heading's TEXT (strip tags, collapse whitespace). Verify on `dist/aied-export.md` (one occurrence), then in the EPUB: exactly two — one `nav.xhtml` TOC entry plus the chapter heading — and one in `toc.ncx`.
14. **The Notice page carries the generation date; it must not reuse the module-level `today`.** Both editions print `Generated: <Month DD, YYYY>`. `build_epub()` binds a LOCAL `today` (a `date` object) and `date_str` for pandoc metadata, so reusing the module-level `today` string emits an ISO date instead. Keep the EPUB and PDF notice text identical, and verify by extracting the text out of both artifacts.

15. **A `## Connected …` heading glued to the previous bullet loses its heading (pandoc ≠ CommonMark).** Most concept pages write `## Connected Articles` directly after the last bullet of `## Connected Concepts`, with no blank line between. That is valid CommonMark and the site renders it right, but pandoc will not let an ATX heading interrupt a paragraph or a list item: it swallows the heading as literal text at the end of the previous bullet, so the reader sees the two Connected lists merged under one heading with a shredded `#### Connected Articles` on the last item, and no TOC entry. `separate_headings()` in `build-epub.py` now inserts a blank line before every ATX heading outside code fences. Do NOT "fix" the source pages instead — the site's rendering is already correct, and the same glue affects `###` subheadings in some bodies. Verify in the export with `grep -c -E "[^ ]\s+#{1,6} "` (must be 0) and `grep -c "^#### Connected Articles$"` (one per concept page).
16. **A bare `[[slug]]` wikilink has no label: use the target page's own title, not a de-slugified guess.** `convert_links()` used `smart_title(slug)`, so the book printed "Well Being" and, worse, printed ENGLISH guesses ("Learners", "Critical Thinking", "Self Assessment") inside translated editions' Connected lists — while the site showed the localized page titles. `PAGE_TITLES` (built from this locale's concepts + FAQs + the articles collection) now mirrors `allTitles` in `src/pages/concepts/[slug].astro`; `faq_titles` was folded into it. Article titles stay English in every edition, because the article pages themselves are untranslated. This also affects inline prose links (`[[llm]]` → "Large Language Models (LLMs)"), which is exactly what the site renders.
17. **Reconcile the connected-section counts against the SOURCE, not a remembered number.** A stored absolute ("217 Connected Articles / 245 Connected Concepts") goes stale as soon as a page is added, and the two counts are not the same population: `#### Connected Articles` appears once per **concept** page, while `#### Connected Concepts` appears on concept pages **and** on every **resource** page (`content/en/resources/*.md` carries `## Connected Concepts` but `## Connected Resources`, not Connected Articles). The gap between the two counts is therefore the resource-page count. Check with `grep -l '^## Connected Articles' content/en/concepts/*.md | wc -l` and `grep -rl '^## Connected Concepts' content/en/ | wc -l`, and compare to the export. In a translated edition the same counts appear under that locale's headings (`#### Artículos conectados`, `#### Conceptos conectados`), so grepping the English strings in `dist/aied-export.es.md` returns 0 and is NOT a defect.
18. **The builder's reported PDF size is larger than the committed file.** `build-epub.py` prints `Built …/aied.pdf (N bytes)` before pikepdf rewrites the PDF to set `/Lang`, so `stat -c%s` afterwards is smaller. Expected — do not read the difference as a truncated artifact, and verify the live file against the on-disk size, not the logged one.
19. **Never bundle a recursive delete into a verification command.** Extracting an EPUB to inspect it tempts a `rm -rf <scratchdir>` prefix; the security scan flags the whole command as destructive, blocks it pending approval, and a silent timeout kills the verification (2026-10-02). Extract into a fresh unique directory (`mkdir -p $D-$(date +%s)`) and leave cleanup out entirely.
20. **A TRANSLATED body opens with the machine-translation note before its title H1, which defeats the leading-H1 stripper and duplicates every FAQ in the TOC.** `process_md()` drops an H1 that repeats the page title, but it stopped at the first non-blank line, and a translated FAQ body is `*Traducción automática…*` then `# <title>`. The H1 survived, was shifted to a chapter heading, and the page appeared twice — once as a chapter, once as a section. The ES EPUB shipped **35 duplicated titles** this way before it was caught (2026-10-02). Fixed by skipping at most ONE leading emphasis-only line while looking for the H1; it never fires for English pages, so only translated editions change. Verify with a Python `collections.Counter` over the nav entry text (`re.sub(r'^\d+(\.\d+)*\.\s*','',t)`), not by eye.
   A handful of duplicates are NOT this bug and are not caused by the leading note: two genuinely distinct pages that share a title, e.g. `Administradores`/`administrator` or `Teorías y marcos`/`theories-and-frameworks`. They are a separate, fixable defect — see pitfalls 22-24, which remove them in the exporter for every locale at once with no new copy. The English edition has the same collision, so compare the two editions' duplicate counts before chasing them.
21. **`xmllint` is NOT installed on this machine, so a well-formedness sweep using it reports EVERY member as malformed.** A `for f in ...; do xmllint --noout "$f" || echo MALFORMED; done` loop therefore emits one false alarm per file (2026-10-02). Parse with Python instead: `xml.etree.ElementTree.parse()` over the extracted `EPUB/` tree, counting failures.

22. **A front-matter chapter's navigational subheadings become TOC entries and can duplicate a chapter or page title.** The home page's "recommended starting concepts" groups render as `<h3>` under the starting-points `<h2>` (`src/components/pages/HomePage.astro:38`) — they are a site navigation widget, not book sections. As headings they entered the TOC and collided with taxonomy chapter labels and concept page titles; in Chinese, `核心概念` was both a starting-point group and the Essentials chapter, and `管理者` both a group and the administrator page. 7 locales hit the chapter class and 9 the page class. Fix: unlist them with the same `{.unlisted}` mechanism the Use-With-AI chapter already uses (`_unlist_h3()`), so pandoc's `--toc` omits them while the body keeps the label and its link list. Audit the whole locale set, not one locale: compare every locale's `taxonomyHeadings` values and `home.<locale>.ts` `heading:` values against that locale's concept/FAQ `title:` values.

23. **An umbrella chapter label and a concept page title can be the same words** — the `Theories and frameworks` chapter holds SAMR and TPACK while the `theories-and-frameworks` page is about the subject generally. English had this too, differing only in case, so an exact-string check misses it. Fix in `build-epub.py` (`_disambiguate_repeated_headings`): qualify the later of any repeated heading with its parent heading's text, which is already translated and needs no new copy. Two constraints that both bite: (a) restrict to `level <= 3`, because the editions build with `--toc-depth=3` — disambiguating H4 and below churns body headings and, in the first cut, rewrote all 220 `#### Connected Concepts` headings; (b) compare `plain.casefold()` so the English case-only pair is caught. Keep the `{#anchor}` OUTSIDE the appended parenthetical or pandoc moves it inside the parens and breaks the link.

24. **A repeated TOC title is a source-naming problem, not a translation error.** The three naming spaces that can collide are the `taxonomyHeadings` chapter labels, the concept/FAQ page `title:` values, and the home page's `groups[].heading` values. Fixing it in the strings means editing ~165 strings across 33 locales; fixing it in the exporter (2026-10-24, pitfalls 22-23) covers every locale at once with no new copy. Prefer the exporter unless the collision is genuinely a wrong string.

## Wikilinks in the EPUB/PDF
- `[[target|label]]` / `[[target]]`:
  - target is a concept or FAQ present in the EPUB → internal anchor `[label](#slug)`.
  - target is an **article** (not in the EPUB) → link out to the live site `https://edtechdev.github.io/aied/articles/<slug>/`.
  - otherwise → plain text.
- Apply redirects (over-reliance→cognitive-offloading, ai-tutoring→intelligent-tutoring, etc.) before resolving.

### Never build the site and the offline editions at the same time

`npm run build` clears `dist/`, and `tooling/build-epub.py` writes its intermediate export to
`dist/aied-export.md` between writing the EPUB and running pandoc for the PDF. Run them together and
the site build deletes that file mid-flight, so the PDF step dies with a FileNotFoundError while the
EPUB lands fine - two artifacts from the same command, one of them silently absent.

Sequence them: content edits, then the site build, then `build-epub.py` on its own, then the llms
dump. While an edition build is running, do not edit content either - the exporter reads the corpus
at its start, so a page written afterwards is missing from the file it produces.

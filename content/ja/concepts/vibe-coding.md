> **Vibe coding** — 大規模言語モデルに反復的に指示を出し、その結果の振る舞いを判断することで、下層のソースコードを直接読んだり編集したりせずにソフトウェアを構築することです。Andrej Karpathyが2025年に「コードの存在を忘れてしまう」ワークフローとして普及させたVibe codingは、自然言語プログラミングとエンドユーザー開発——このナレッジベースでは同義語として扱われている定式化——のLLMネイティブな実現であり、散文が主要なプログラミングインターフェースとなります。

## 考えるべき問い

- Karpathyの元の定式化は、「コードの存在を忘れてしまえ」というものでした。先読みを続ける前に自問してください。コードを見ないことは特徴（障壁を下げる）でしょうか、それともリスク（見えないものは検証も修正もできない）でしょうか。その答えは、誰がVibe codingを許されるべきかに何を含意するでしょうか。
- Vibe codingで成功するのは誰かについての研究では、ユーザーがコードに一切触れない場合でも、従来の[[cs-education|計算機科学の成績]]が依然として成功を予測することがわかりました。それが意外に感じるなら、CSの訓練が散文だけでは捉えられないどんな隠れたスキルを築いているでしょうか。
- 同じ研究では、執筆スキルがVibe codingのパフォーマンスを予測するのは、主に*それがより高品質なプロンプトを生むから*だとわかりました。プロンプト作成が本当にボトルネックなら、正しい対処は[[prompt-engineering|人々により良いプロンプトの作り方を教えること]]でしょうか——それとも、散文スキルをそれほど要求しないようにツールを再設計することでしょうか。
- Vibe codingはしばしば「誰でも」開発者にすると称賛されます。しかし執筆スキルとCS知識の両方が成果を形作るなら、Vibe codingはソフトウェア構築へのアクセスを広げるのでしょうか、それともスキルの障壁をコードから散文に移すだけでしょうか。
- 一部の開発者は「純粋な」Vibe coding（コードを一切読まない）と、モデルが書いたものを確認・編集するAI支援のコーディングを区別します。真の学習——[[cognitive-offloading|過度な依存]]との対比で——はどちらでより起きやすいと思われますか、それはなぜでしょうか。

## はじめに

Vibe codingは、LLM統合の開発プラットフォーム（Replit、Lovable、Cursorなど）によって可能になる相互作用スタイルを指します。ユーザーが自然言語でプログラムを指定し、モデルが動作するシステムを生成し、ユーザーはソースを編集するのではなく観察された振る舞いに基づいて反復します。この用語は、モデルへの依存度が高くなり「コード」が意識から薄れていく経験を捉えるため、OpenAI共同創業者のAndrej Karpathyが2025年2月に作りました。Vibe codingは、このナレッジベースが既に追跡している複数の流れの収束点に位置します——[[cs-education|プログラミング]]に応用された[[generative-ai|生成的AI]]であり、[[prompt-engineering|プロンプト駆動]]の仕事の極端な形であり、[[human-ai-collaboration|人間とAIの協働]]の具体例であり、[[teacher-role|非プログラマー]]やエンドユーザーが自分たちのソフトウェアを構築するための最も明確な道筋（エンドユーザー開発）です。

深い根源もあります。日常語でプログラミングするという考えはLLMよりずっと古くからあります——「非専門のプログラマーのための英語プログラミングシステム」であろうとしたCOBOLの野心、Donald Knuthのリテレートプログラミング、制約された英語の部分集合による自然言語プログラミングの研究までを遡ります。LLMによって初めて、本質的に会話的で指定不足の指示を実行可能なコードに写像することが実現可能になりました。Vibe codingは、ユーザーが意図的に生成されたソースを検査も編集もせず、反復的なプロンプト作成と行動評価だけに頼る、その特別な変種です。

### 構成概念の定義：「純粋な」Vibe codingとコード可視のVibe coding

Vibe codingの定義は今も流動的です。ある者は広くAI誘導のプログラミング一般を指す言葉として使い、ある者は厳密に「LLMで、それが書くコードを検証せずにソフトウェアを構築すること」を指すと主張します。Google Cloudは、Karpathyの定義と整合する「純粋な」ノーコード版と、ユーザーが生成されたコードを理解し洗練させる版を区別しています。この区別は[[research-methods-aied|研究]]にとって重要です。Vibe codingの熟達度を扱う統制研究には、よく定義された構成概念が必要です。Vibe coding熟達度の予測因子に関するCHI 2026の研究は、意図的に「純粋な」ノーコード変種を標的にしました——参加者は生成されたソースを見ることも編集することもできなかったため、測定されたパフォーマンスは、散文と観察された出力だけを通じて振る舞いを指定し、洗練させ、デバッグする能力を反映しました（[[vibe-coding-writing-cs-achievement-2026|Thorgeirssonら]]参照）。

### Vibe codingで成功するのは誰か：証拠

事前登録された横断研究（N = 高等教育機関の学生100名）は、どのスキルがVibe codingの成功を予測するかについての最初の統制された参加者レベルの証拠を提供します。[[writing-education|書面コミュニケーション能力]]（r = .29）と計算機科学の成績（r = .39）の両方が、専門家が検証したGUI志向のVibe coding課題におけるパフォーマンスを有意に予測し、領域一般的な認知スキルを統制した後も計算機科学の成績は有意なままでした（偏相関r = .281）。合同モデルでは、計算機科学の成績が執筆スキルの約2倍の固有分散に寄与しましたが、両者が独立した予測価値を加えました。決定的に、人間が評価したプロンプトの質が執筆→パフォーマンスの関係を媒介し、明確な散文がより良いプロンプトを生むことで作用するという応答プロセスの証拠を与えています。環境がソースコードを隠していたため、CS知識は間接的にしか（問題の分解、アルゴリズム的思考、制御フローの心的モデルを通じて）助けられなかった——したがって著者らは、自分の推定は、ユーザーがコードを直接編集することもあるAI支援プログラミングにとっては*下限*だと論じています（[[vibe-coding-writing-cs-achievement-2026|Thorgeirssonら、2026]]）。

### エンドユーザー開発と教員向けツールとしてのVibe coding

Vibe codingの大きな約束は、非プログラマー——[[teacher-role|教師]]や領域専門家を含む——が自分たちのソフトウェアを構築できるようにする、LLM時代のエンドユーザー開発の一形態であることです。[[gaide-vibe-coding-k12-teachers|GAIDEフレームワーク研究]]では、K-12の教師（非プログラマー）が8週間のワークショップでVibe codingを使ってAI搭載の学習ツールを作り、自身の[[ai-literacy|AIリテラシー]]を高め、「作ることによる学習」を専門職開発モデルとして実証しました。高等教育では、ある教員が[[vibe-coding-programming-process-visualizer|IDEの活動ログからのプログラミングプロセス可視化ツール]]を数日でVibe codingにより素早く構築し、学生のプログラミングプロセスを教授と[[academic-integrity|学術的誠実性]]の検討のために可視化しました。これらの事例は、Vibe codingを単なる学習者のスキルとしてではなく、[[educational-development|教育技術を作れる人を再形成する]]制作能力として位置づけています。

### デザインの同質化：多様性のないアクセス

Vibe codingのエンドユーザー開発の約束は、誰が作れるかについてであり、何が作られるかではありません。あるコースの展開では、単一のVibe codingプラットフォームで73人の学生が別々の事業のサイトを構築して生み出されたのは約12の異なるデザインで、作者意識は測定された独創性と対応しませんでした（[[vibe-coding-design-diversity-2026|Boussiouxら（2026）]]）。構築の障壁を下げることは、成果を標準化しかねません——アクセスの約束が宣伝しないコストです。

### 学習、主体性、そして過度な依存のリスク

Vibe codingは、AIが実装を自動化するとき何が学ばれるかという中核的な問いを再び開きます。ユーザーはコードを読まないため、モデルの振る舞いを信頼しなければなりません——これはVibe codingを、AI支援プログラミング全体を貫く[[agency|主体性]]と[[cognitive-offloading|過度な依存]]の緊張の高リスクな事例にします。カリキュラムは、実装の教授から、AI生成の成果物をどう指示し、検証し、監査するかの教授へと移行することで応答しています（[[reshaping-cs-education-genai|学部の計算機科学教育の再形成]]と[[agentic-ai|エージェント的ソフトウェア工学]]参照）。Vibe codingはまた学習者の認識論的な立場も変えます。成功はコードを書くことよりも、意図を正確に表現し振る舞いを目標に対して評価することに依存し、伝統的な構文の習得よりも[[computational-thinking|計算的思考]]と構造化された執筆に近い力量に依存します。

第二の限界は構築そのものに現れます。コーディングの障壁を取り除いても、診断の負担はそのまま残りうるのです。2つの工学の事例研究では、ある教員が平易な言葉でGeminiに指示することで、電池熱管理システムと3つのARQプロトコルの動作するWebシミュレーションを数時間で構築しました（[[caee-vibe-coding-simulation-development-engineering-education-2026|Tarasakら（2026）]]）。その後、必要な振る舞いを明記した指示を含む反復的なプロンプトを経ても、重複パケットのエラーは残りました。教員がプロトコルの振る舞いからタイムアウト間隔が不十分であると推論したときに初めて修正され、その間隔はインターフェースが決して露出しなかったパラメータでした。どちらのシミュレーションも学習への影響は測定されていないため、この記録は有効性ではなく実現可能性を立証するものです。

### 関連概念との接続

Vibe codingは自然に[[prompt-engineering|プロンプトエンジニアリング]]（プロンプトの質が散文駆動の開発のメカニズム）、[[cs-education|計算機科学教育]]（その技法が最も使われ最も議論される領域）、[[computational-thinking|計算的思考]]（コードへのアクセスなしでも成功を予測する心的モデリング）、[[writing-education|執筆教育]]（執筆がプログラミングスキルになること）、そして[[agentic-ai|エージェント的AI]]（モデルを成果物へ向けて指示すること）と接続します。[[ai-literacy|AIリテラシー]]や[[teacher-role|教師の役割]]とも交差します。自分自身のツールを構築する能力が、教師と学習者に何ができるかを変えるからです。最後に、[[academic-integrity|学術的誠実性]]と計算機教育全体でAIコード生成が提起するのと同一の評価の問いを提起します。

このナレッジベースの教員レベルの事例研究が、組織的な層を補います。[[zimmer-ai-intrapreneurship-faculty-innovation-2026|Zimmer（2026）]]は*AIイントラプレナーシップ*——教育者が制度的な調達を待たずに自分たちのツールを構築すること——を記述しており、コードを書かない著者がClaude Codeを使って321のコースリンクのためのチェッカーを構築した例を含みます。決定的な実現要因は技術的ではなく組織的でした。仕事の裁量、報酬、時間の利用可能性で、最後のものは学術的な場で最も明らかに欠乏しており、昇進とテニュアによって損なわれると記述されています。セキュリティの見通しは冷静なままで、Veracodeの2025年の分析ではAI生成コードのうち安全なのは55%のみだったため、Vibe codingされた教室用ツールも、学生データを扱ったりLMSに接続したりする前に検討の段階を必要とします。

## よくある誤解

**「Vibe codingはスキルの障壁を下げるので、主にうまく書くことの問題である。」** 書面コミュニケーションの熟達は助けになりますが、成果を単独で担うものではありません。事前登録された横断研究（N = 100の高等教育の学生）では、[[writing-education|書面コミュニケーション能力]]（r = .29）と計算機科学の成績（r = .39）の両方が、専門家が検証したGUI志向のVibe coding課題のパフォーマンスを有意に予測し、合同モデルでは計算機科学の成績が執筆スキルのおよそ**2倍の固有分散**に寄与しながら、両者が独立した予測価値を保ちました。障壁は消えたのではなく移り、その一部は技術的なままです。

**「誰もがソフトウェアを作れるようになったのだから、作られるものはより多様になる。」** アクセスと多様性は別の成果であり、アクセスは二つ目を圧縮しさえしえます。このコーパスのデザイン同質化の証拠はまさにそのパターンを記述しています。同じモデル、同じ部品の慣習、同じプロンプティングの既定から働く、より広い作り手の集団は、収束するデザインへと傾きます。著作の民主化は、成果物の多様化を自動的にはしません。

**「『純粋な』Vibe codingこそがこの用語の意味であり、区別は重要でない。」** それは評価と安全のために重要です。このページは、ユーザーが意図的に生成されたソースを検査も編集もせず、反復的なプロンプト作成と行動評価だけに頼る純粋なVibe codingを、ユーザーが生成されたものを読むコード可視の仕事から区別しています。これらは異なる誤りのプロファイルを持つ異なる活動であり、一方の研究が他方についての主張を許すわけではありません。

**「アプリが動けば、生成されたコードは問題ない。」** 動くことは弱い検証です。Veracodeの2025年の分析ではAI生成コードのうち安全なのは55%のみだったため、Vibe codingされた教室用ツールも、学生データを扱ったり保護に値するシステムに接続したりする前に検討の段階を必要とします。行動評価は、ユーザーがたまたま通った経路を確認するだけで、通らない経路については何も言いません。

## Vibe codingを実践に移す

**教員と教師教育者のために**

- 純粋なVibe codingとコード可視のVibe codingの違いを明示的に教え、学生データを扱うものには二つ目を要求してください。この区別は教えられる習慣であり、哲学的な趣味ではありません。
- Vibe codingの仕事と並んで実際のプログラミングの筋を保ってください。計算機科学の成績がおよそ2倍の固有の予測分散を担ったからです。自然言語の仕様を完全な代替として扱うことは、より強い予測子を捨てることです。
- 学生に成果物を行動的に評価させ、*かつ*配備するもののソースを検査させてください。生成されたコードを読むことはレビューのスキルであり、プロンプトを打てる学生にとって自動的ではありません。

**開発者と管理者のために**

- 学生の記録に触れる前に、Vibe codingされたツールにセキュリティレビューの段階を走らせてください。55%という安全なコードの知見と整合します。
- 同質化のための予算を取ってください。複数の職員が同じ既定から同じ種類のツールをVibe codingするなら、似た出力を予期し、差別化をどう意図的に達成するかを計画してください。
- 維持されるツールにはコード可視のワークフローを好み、純粋なVibe codingは使い捨ての試作に残してください。

**研究者のために**

- 成果と並んでVibe codingの条件（純粋かコード可視か）を報告し、自己申告の成功ではなく専門家が検証したGUI志向の課題を用いてください。結果が研究をまたいで比較可能になります。
- アクセスの議論を検証しているなら、成果物の数や作り手の数だけでなく、成果物の多様性を測定してください。
